# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Read first

- `HANDOFF.md` is the first thing to read: where the project stands, decisions already made, how the owner likes to work, and state that lives outside the repo (secrets, users, CI). `TODO.md` is the checklist; `REVIEW_SUMMARY.md` / `REVIEW_TODO.md` are the latest review and its task list.
- Each workspace has its own `CLAUDE.md` with its commands, architecture and test traps: `infra/`, `packages/core/`, `packages/graphql/`, `packages/web/`. Read the one you are about to work in.
- `PLAN.md` is the original design (schema, API, auth, build order); the Alexa and Echo parts of it are shelved. `CONTEXT.md` is an older handoff and is partly stale. The plan was partly written from memory, so verify any package or version it names against the registry (`npm view <pkg>`).
- The app is built and deployed (the web app, the API, the infra). The Alexa skill and Echo widget were shelved on 2026-11-10; do not treat them as planned work.

## Commands

Node 24 (`.nvmrc`), Yarn 1.22 classic. Run from the repo root.

```bash
yarn typecheck                                # root tsc --noEmit, then `yarn workspaces run typecheck` (deliberately not `tsc -b`)
yarn build:web                                # builds packages/web/dist; the CDK stack publishes it, so `cdk synth`/`diff`/`deploy` fail without it (the infra tests do not need it: they set the `webDist` context to infra/placeholder)
yarn test                                     # vitest run, all projects
yarn test --project infra                     # one project
yarn test:watch
# live DSQL tests (`*.live.test.ts`) skip unless DSQL_ENDPOINT is set; they need AWS credentials and AWS_REGION
zsh -ic 'assume agiannell >/dev/null 2>&1; export AWS_REGION=us-west-2 DSQL_ENDPOINT=<cluster>.dsql.us-west-2.on.aws; yarn vitest run packages/core/test/withTransaction.live.test.ts'
yarn vitest run infra/test/foo.test.ts                    # single file
yarn vitest run infra/test/foo.test.ts -t "name"          # single test
```

A throwaway local Postgres can stand in for DSQL in live tests (`LOCAL_PG_URL`) and for regenerating `schema.ts` when you should not migrate the real cluster first; its output matches the cluster's. The recipe is in `packages/core/CLAUDE.md`.

`packages/core/src/schema.ts` is generated by `kysely-codegen` from the live database, with overrides in `packages/core/.kysely-codegenrc.json`; never edit it by hand. Regenerate after every migration. It connects with plain `pg`, so the IAM admin token goes in the URL (URL-encode it). If it fails with `EHOSTUNREACH` on an IPv6 address, add `NODE_OPTIONS=--dns-result-order=ipv4first`:

```bash
H=<cluster>.dsql.us-west-2.on.aws
T=$(aws dsql generate-db-connect-admin-auth-token --hostname $H --region us-west-2)
E=$(python3 -c 'import sys,urllib.parse;print(urllib.parse.quote(sys.argv[1],safe=""))' "$T")
DATABASE_URL="postgres://admin:${E}@${H}:5432/postgres?sslmode=verify-full" yarn workspace @gnl-books/core codegen
```

`jsonb` columns (`books.authors`, `shelf_entries.tags`) are written as `JSON.stringify(...)` text, because `pg` would send a JS array as a Postgres array, which `jsonb` rejects. Reads come back already parsed. The types encode this.

Run tests from the repo root only. Projects are defined inline in the root `vitest.config.mts` (`infra` has the CDK cleanup setup file; `packages` is node-only and skips `packages/web`; `web` runs the SPA's tests in happy-dom with Testing Library, because jsdom 31 needs Node 24.15 or later and the author's machine has 24.12). `packages/web/test/auth.live.test.ts` hits the real Cognito discovery endpoint and only runs with `VITE_LIVE_COGNITO=1`. Running Vitest from inside a workspace finds no config and silently drops the setup file and timeout, so workspaces have no `test` script. Every workspace needs a `typecheck` script, or the root `yarn workspaces run typecheck` errors. `vitest run` exits 1 when a project has no tests yet. Only the web workspace has a lint script (`yarn workspace @gnl-books/web lint`, oxlint); CI does not run it.

## Architecture (big picture)

A family reading tracker: a web SPA over a GraphQL API and one dataset. (An Alexa skill and an Echo Show widget were planned as further clients and are shelved, so the API is shared by the web app alone for now, but it stays a real API rather than direct DB reads from the UI.)

- `packages/core` is the keystone: domain logic, Kysely queries, DSQL connection, Hardcover client, CSV export. **The GraphQL Lambda and the migration runner import it directly.**
- `packages/graphql`: Pothos schema plus Apollo Server 5 in one Lambda. All logic lives in `src/schema.ts`; `src/lambda.ts` and `src/dev.ts` are thin wrappers and must stay that way so local and deployed behavior don't drift.
- The SPA and the API share one CloudFront distribution (API at `/graphql`), so there is no CORS.
- Data scoping: every query is scoped by `familyId` at the data layer. Never trust an ID from the client.
- Kids are profiles, not Cognito accounts. A parent PIN gates sensitive actions.
- Sign-up is open. A new user (no `accounts` row) makes a family or asks to join one by naming a parent's email; a parent approves it behind the PIN (`packages/core/src/joinRequests.ts`). Asking must stay indistinguishable whether or not the email belongs to a family. The API gets a user's email from Cognito (`AdminGetUser`, verified only) because the access token it checks has none; never take an email from the client.
- Voice (shelved): it would be adult-only, because Amazon Kids mode refuses the skill; if it is ever revived, resolve the reader by `personId` first, otherwise ask "Who's reading?", never guess, and keep the `alexa::person_id:read` scope in the manifest. The design is in `PLAN.md`.
- The per-person data model is a superset of the Goodreads export CSV; `shelf` uses Goodreads' exact `Exclusive Shelf` values so export is a pass-through. The CSV writes both `Bookshelves` and `Exclusive Shelf`.

### Aurora DSQL rules that shape the code

- Primary keys are random UUIDv4 generated in app code, not UUIDv7 (avoids a write hotspot).
- Concurrency is optimistic: `core` opens every transaction through `withTransaction()` (`packages/core/src/db.ts`), which wraps Kysely's `db.transaction().execute()` in `withRetry()`. DSQL reports conflicts as `error.code` `OC000` / `OC001` / `40001`, and `isRetryable` reuses the connector's `isOCCError`. The connector's own `pool.transaction()` is deliberately not used, since Kysely issues its own BEGIN/COMMIT. Transaction logic must be idempotent.
- Migrations: one DDL statement per transaction, DDL separate from DML, retry `OC001`. Use `CREATE INDEX ASYNC`. No triggers, PL/pgSQL, temp tables, or `TRUNCATE`. Max 3,000 rows modified per transaction.
- Connect with the official `@aws/aurora-dsql-node-postgres-connector`; treat connections as disposable.
- The API Lambda connects as the limited role `gnl_books_app` (`DSQL_USER`): row access only, no schema changes. Only the migration runner is `admin`, and after the migrations it calls `provisionAppRole` (`packages/core/src/appRole.ts`). A new table needs no extra grant (default privileges); a new kind of access does. Locally and in live tests `DSQL_USER` is unset, so they connect as `admin`. The wiring is in `infra/CLAUDE.md`.

## Working conventions

- Install with `yarn add`; initialize with the ecosystem's own tool (`cdk init`, `create-vite`, `ask new`). Don't hand-type version ranges into `package.json`. Use `npm init` for a bare manifest, not `yarn init`.
- The web UI is **Radix Themes** with plain CSS, because the site's content security policy (`infra/lib/gnl-books-stack.ts`) allows no inline `<style>` or scripts and a static site cannot use nonces. Do not add CSS-in-JS or a Radix component that injects a style tag (Dialog, Select, Popover, DropdownMenu) without loosening that policy on purpose. The full list of limits is in `packages/web/CLAUDE.md`.
- Pins that are deliberate: TypeScript `~6.0.3` (fallback `~5.9.x` if tools complain; 7 is unconfirmed and has proven incompatible in practice), `@types/node` 24 to match the Node 24 Lambda runtime. Say why when pinning on purpose.
- One TypeScript version across the whole repo, owned by the root `package.json`. Scaffolders (`cdk init`, `create-vite`) pin their own, often 7: remove `typescript` and `@types/node` from the workspace after generating it, so there is no second copy. Verify with `yarn why typescript` or `grep '^"\?typescript@' yarn.lock`.
- Vitest is the test runner in every workspace, including `infra` (the CDK template's Jest is removed). Vitest 5 needs `vite` as a devDependency, which Yarn classic doesn't install for you.
- Write files with the Write/Edit tools, never Bash heredocs or redirects, one file per call, with a short what/why above each change.
- The repo is public: keep AWS account IDs, hosted-zone IDs, and personal details out of committed files. Use the `<AWS_ACCOUNT_ID>` / `<HOSTED_ZONE_ID>` placeholders; real values come from the deploy environment and `cdk.context.json`.
- Ask before outward-facing actions (pushing, creating remote resources, deploying).
- CI: `.github/workflows/test.yml` runs on push and PR; `deploy.yml` is manual (`workflow_dispatch`) and the owner runs it. The deploy runbook is in `HANDOFF.md`.
- Keep `.npmrc` and `.yarnrc` pinned to the public npm registry. In this workspaces repo Yarn 1 ignores `.npmrc` and reads `~/.yarnrc`, which on the author's machine is a private Artifactory mirror, so mirror URLs can land in `yarn.lock` (CI then fails with a 401 and checks `yarn.lock` for non-public hosts). The project `.yarnrc` covers commands at the repo root but **not** `yarn workspace <ws> add`: pass `--registry https://registry.npmjs.org`, or rewrite afterwards with `sed 's#https://<mirror host>/artifactory/api/npm/npm/#https://registry.npmjs.org/#g'`.
